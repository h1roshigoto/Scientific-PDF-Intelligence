# Проверка готовности официальной выгрузки

Запускайте из корня репозитория на Windows с установленным `spi` и локальными артефактами test. Для сверки цитат обоим чекерам нужен `pypdf`. Для разработки и проверки команд используйте `python -m pip install -e '.[dev]' pypdf`.

```powershell
python -B -X utf8 -m spi.release_readiness
$releaseCode = $LASTEXITCODE
```

Команда сверяет 90 Solar и 90 RAG, регистрации, SHA-256 и число физических страниц. Она читает исходные PDF и проверяет Store на временной копии. `report.json` и `scope-review-pending.csv` сохраняются в новом каталоге `%TEMP%\spi-release-*`, путь печатается в терминале. Реестр содержит идентификаторы, SHA-256, названия, ссылки на локальные PDF, основания, страницы для начала проверки, доступные указатели на evidence и состояние checkpoint. Предложения обозначены `proposal only`. Диагностика относится к локальному корпусу, храните её рядом с остальными локальными материалами.

- `PASS` (0) — обе выгрузки и оба участнических чекера прошли. Сохранён `candidate/solar` и `candidate/rag` во временном каталоге.
- `BLOCKED` (2) — требуется действие по входным данным, согласованию scope, научному gate или замечаниям чекера.
- `FAIL` (1) — обнаружена техническая ошибка. В отчёте есть этап и диагностика.
- `NOT RUN` — этап пропущен. `UNKNOWN` — сохранённых данных недостаточно для подсчёта.

При других локальных путях используйте параметры из `python -m spi.release_readiness --help`. Нужны `data/<track>/test`, снимок Store (реестр, scope и batch checkpoints), каноническая очередь P0 №21, манифест прежних решений, лист согласования и оба участнических комплекта. `--solar-template` принимает папку с семью CSV Solar. `--rag-template` принимает семь CSV RAG и `schema.json`. `--contracts` указывает на общий родительский каталог `solar/tools/check_submission.py` и `rag/tools/check_submission.py`. Версии и точный порядок колонок сверяются с `passport.md` и схемой SPI. Манифест RAG содержит `official_rag_template: false` для участнической адаптации `rag-viniti-adaptation-1.0`.

## Ручное согласование

Данил копирует существующий лист в отдельный рабочий CSV. Путь к нему передаётся через `--approval`. Для проверки сначала можно использовать исходный лист в режиме чтения.

```powershell
$source = 'outputs/p0-22-release/scope-approval.csv'
$review = Join-Path ([IO.Path]::GetTempPath()) ('spi-scope-' + [guid]::NewGuid() + '.csv')
Copy-Item -LiteralPath $source -Destination $review
python -B -X utf8 -m spi.release_readiness --approval $review
```

В Excel импортируйте лист как UTF-8 с запятой. Для каждого финального решения внесите `in_scope` или `out_of_scope` в `human_decision`, имя в `reviewer`, фактическое основание в `comment` и физические номера страниц в `source_pages` в виде JSON, например `[1, 4, 7]`. После сверки человек устанавливает `human_approved=TRUE`. Для незавершённой проверки оставьте подтверждение пустым или `FALSE`. Существующие четыре решения из манифеста сверяются с Store и текущими PDF.

Станислав сверяет спорные RAG P007 и P010 по одному определению извлечения демонстраций задачи. У P007 проверьте стр. 4–5, 7–8 и 14, у P010 стр. 1, 5 и 8. Для утверждения пары запишите один непустой `rag_demo_criterion` в обеих строках. Для включённых публикаций отдельно сверяются первичный или цитируемый источник, контекст условий и числовые значения. В Solar проверьте устройство, измерение и единицы, прежде всего для публикаций без `verified`. В RAG проверьте набор данных, задачу, метод, генератор, протокол и источник как единый контекст. `metric_k` относится к метрике, а `top_k` к настройке поиска.

Если в каноническую очередь добавлены публикации, используйте отслеживаемый генератор на рабочей копии, закрытой в редакторе.

```powershell
python -B -X utf8 -m spi.build_scope_sheet $review `
  --queue 'outputs/p0-21-test-local/scope-human-review.csv' `
  --metadata 'outputs/p0-22-release/review-metadata.json' --append
```

Генератор добавляет новые строки с пустыми полями решения. Перед обновлением он проверяет идентификаторы и SHA-256, при изменениях создаёт резервную копию и атомарно обновляет лист. Повторный запуск с теми же данными сохраняет файл побайтно. Старые строки остаются на месте, даже если источник очереди перестал их перечислять. Перед релизом такое расхождение нужно сверить по исходному реестру и очереди. Параметр `--append` нужен только для обновления существующей рабочей копии.

## После merge

```powershell
git switch main
git pull --ff-only
$testDir = Join-Path ([IO.Path]::GetTempPath()) ('spi-pytest-' + [guid]::NewGuid())
python -m pytest -q --basetemp $testDir
python -B -X utf8 -m spi.release_readiness --approval $review
```

Для выхода из `BLOCKED` завершите ручной scope и научную проверку включённых работ. В отчёте смотрите незавершённые checkpoints, публикации без verified, `needs_review`, `unresolved`, OCR и ошибки валидации. При необходимости получения новых извлечений или OCR согласуйте отдельный запуск и сохраняйте происхождение данных. Dry-run читает подтверждённые решения для временной проекции в памяти.

Кандидат появляется после `GO` на обоих треках, завершённых checkpoints включённых публикаций, отсутствия ошибок научной проверки, проверки связей SPI и обоих участнических чекеров. Контроль покрытия и цитат оценивает имеющиеся записи. Полноту по PDF и приложениям подтверждает независимая предметная сверка. После неё Данил переносит принятые `candidate/solar` и `candidate/rag` в согласованное место сдачи и сверяет SHA-256 всех 14 файлов с кандидатом. В каждый комплект входят семь CSV и только предусмотренные шаблоном данные. JSON-отчёт, логи и реестр служат внутреннему сопровождению выпуска.
